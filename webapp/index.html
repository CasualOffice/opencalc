Why OpenCalc

A spreadsheet core built like a compiler.

Loss-aware fidelity

Content the model can't represent is preserved or reported — never silently dropped. A semantic fixed point is gated: import → write → import yields an equal model.

Deterministic

Same input + version ⇒ the same model, values, layout, and bytes. Every layer is golden-testable; the writer is byte-stable.

Embeddable anywhere

No mandatory DOM, server, or UI framework. One Rust core drives a Tauri desktop app, a WebAssembly grid, and headless batch jobs alike.

Fast by design

A virtualized grid targets a million cells at 60 fps, and edits trigger an incremental recalc — only the changed cell's dependents are recomputed, not the whole book.

A real editor

Freeze panes, merges, sort & filter, a rich clipboard, formula autocomplete, number formats, borders — a canvas grid that behaves like the spreadsheet you already know.

Open source, in Rust

edition 2024, unsafe forbidden, a layered crate DAG from model and parser up to layout and render. Read every line.

Under the hood

One pipeline, three hosts.

A layered crate DAG: parsing sits below evaluation, so import and editing use the formula AST without pulling in the calc engine.

.xlsx / csv → import → model → calc → layout → render

Native / Tauri

The full SDK — open, edit with undo, recalc, lay out, render, save — as a desktop app.

WebAssembly

The same core compiled to wasm32, driving a canvas grid entirely client-side. This page is proof.

Headless

No UI at all — batch convert, recalc, and render workbooks to PNG on a server.

embed the engine
// One session composes every layer: open, edit, recalc, render, save.
let mut session = WorkbookSession::open(bytes)?;
session.edit(Operation::SetCell { sheet: 0, at: a1("B2"), cell })?;  // incremental recalc
let png = session.render_png(0, &viewport)?;             // virtualized grid → PNG
let xlsx = session.save()?;                              // deterministic .xlsx
