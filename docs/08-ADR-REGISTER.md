# 08 — ADR Register

Architecture Decision Records capture decisions that are expensive to reverse —
the ones listed under "ADR triggers" in
[11-DESIGN-FIRST-PROCESS](11-DESIGN-FIRST-PROCESS.md). Each ADR has a stable
number, a status, and a short rationale. ADRs are **append-only**: a superseded
decision is marked `Superseded by ADR-NNN`, not edited away.

## Status values

`Proposed` · `Accepted` · `Superseded` · `Rejected`

| ADR-008 | Backend-neutral display list + CPU raster backend | Accepted | Layout emits a serializable display list; `casual-calc-render` executes it on `tiny-skia` with `skrifa` glyph outlines. See [30](30-PERFORMANCE-AND-CAPACITY-TARGETS.md), [42](42-GRID-LAYOUT-AND-RENDERING-ARCHITECTURE.md). |
| ADR-010 | Deterministic, byte-stable snapshots | Accepted | The normalized model serializes to deterministic JSON with `deny_unknown_fields` + `skip_serializing_if`, so additive schema changes keep old golden snapshots byte-identical. |
| ADR-011 | Server-mediated operational transform, not a CRDT | Accepted | Concurrent editing reconciles by OT over the existing closed op set, with a server imposing the total order; document state is a **snapshot plus the ops since it**. Decided by the per-cell byte ceiling (ADR-004) — which CRDT metadata would consume in every single-user session — and by documents originating as `.xlsx` snapshots with no causal history to merge. One editor needs no server at all; sessions run on serverless compute. Presence is a separate ephemeral channel, never transformed. Costs bounded-offline and no peer-to-peer, both accepted. See [56](56-COLLABORATION-CONCURRENCY-DESIGN.md). |

| ADR-012 | Collaboration server: a session, not a filing system | Accepted | The server coordinates co-editing and carries auth, admin, telemetry and configuration; the integrator keeps the document of record and receives finished bytes through a **webhook callback**. OnlyOffice's shape, not Excalidraw's — a relay that sees only ciphertext cannot transform, so that path would reopen ADR-011 rather than deploy it. A session starts from the **original file**, never a model snapshot, or ADR-007's retained parts are silently dropped. **A cluster of interchangeable nodes**: a client connects to any of them, one node **leads a given document** and the rest relay to it so the hot path stays in memory, and the leader's appends are **conditional on the revision** so a stale leader is rejected rather than believed — leadership is an optimisation for latency, the conditional append is what makes divergence impossible. Leadership is internal and moves on its own; it is not a sticky session, which is affinity a *client* is subject to. Kafka's topology per document: the leader replicates to **in-sync replicas** so failover is a promotion rather than a rehydrate, acknowledges only *after* replication, refuses writes when redundancy drops below the minimum, and **never** promotes an out-of-sync replica. A leader **epoch** fences zombies, which is what makes a cheap TTL lease safe. **Standalone needs no Redis at all** — one process, leader by definition; a cluster adds a lease and pub/sub, where Redis provides liveness and the epoch provides correctness. The **token is the whole integration contract** — it carries where to fetch and where to send back, so the server holds a signing secret per tenant and no per-document state at all. Clients receive the model snapshot and do not save in a session; the server does, holding both the ordered document and its retained parts. The server is a *host*, not an engine layer: it lives under `server/` and nothing in `crates/` may depend on it. See [57](57-COLLABORATION-SERVER-BOUNDARY.md). |

| ADR-013 | Interned ids are indices, and cost like one | Accepted | `StyleId` and `StringId` become `NonZeroU32` instead of a 128-bit `Id`. They were **already** indices — `id_for` packed a `u32` into a `u128` with a constant namespace tag — and the tag re-checked at runtime what distinct newtypes already prevent at compile time, while not delivering the cross-workbook safety its shape suggests (COL-12). **Measured: a cell falls from 80 bytes to 32**, 88 to 40 per stored cell, 40 MB rather than 88 MB at the 1M-cell target. Costs a snapshot-format change, so `SCHEMA_VERSION` goes 0 → 1. See [58](58-INTERNED-ID-WIDTH.md). |
| ADR-014 | The collaboration service's stack: transport, identity, coordination, durability | Accepted | Clients speak **WebSocket** to an `axum` server — the protocol is already message-shaped, and a WebSocket pins a *connection*, not a client identity, so it is not the sticky session ADR-012 rules out. Identity is a **host-signed JWT verified against a JWKS endpoint**: the server can verify a token and cannot mint one, and rotation is the integrator's business alone. A cluster coordinates through **Redis** doing three jobs with three primitives — `SET NX PX` leases fenced by the epoch, pub/sub for relay fan-out, Streams for the op log — and **standalone uses none of it**, which is a first-class mode rather than a degraded one. An operation is **appended to the log before it is acknowledged**: acknowledging first is faster and loses edits that every participant's screen still shows, which is silent data loss with a receipt. `acks=all` remains configurable, with the caveat that it needs a separately-enforced minimum in-sync count or the guarantee evaporates when the in-sync set collapses to the leader. See [59](59-COLLABORATION-SERVICE-STACK.md). |
| ADR-015 | Resuming a collaborative session after a disconnect | Accepted | A dropped socket lost unacknowledged edits silently (the rejoin snapshot replaced the workbook holding them) or duplicated them silently (`ClientId` came from a per-connection counter, so a reconnecting participant was a new client and `(client, seq)` duplicate suppression did not apply). A **client-generated resume key**, scoped to the authenticated user, maps back to the same `ClientId` — scoped, because otherwise anyone holding a valid token for the document could present another's key and have their submissions suppressed; client-generated rather than derived from the user, because one person in two tabs is two participants. A resumed client is sent **what it missed, not a snapshot**, so its document stays continuous and its unsent operations still mean something against it; the missed operations travel *inside* `Resumed` so it cannot resend before rebasing. It resends with its **original sequence number**, which the server answers `Duplicate` to if it already had it. Too far behind to catch up is said with `TooFarBehind` **before** the replacing snapshot, so the loss is audible. See [61](61-COLLABORATION-RESUME.md). |
| ADR-016 | Pipelined submissions and cumulative acknowledgement | Accepted | A client sent one chunk and waited to be acknowledged before sending another, costing a round trip per chunk — on a 200 ms link, about five submissions a second however fast anyone types, and the *other* participants wait too, because the next batch was never sent. The obstacle was that a second chunk is written on top of the first before the first has been ordered, so naming the same base has the server rebase it against a chunk it already contains: transformed twice, landing wrong, silently. A submission's base is now `Revision(n)` **or** `Chained`, and the server resolves `Chained` from the table that already records where each client's last chunk landed — sound because one client's chunks arrive in order on one connection. A `Chained` chunk from a client with nothing accepted is refused rather than guessed at. `Ack` becomes cumulative (`through`), which makes a lost acknowledgement self-healing. Outstanding chunks are bounded, degrading to stop-and-wait under pressure. No selective acknowledgement: operation 2 has no meaning without operation 1. See [62](62-COLLABORATION-PIPELINING.md). |
| ADR-017 | How a node that does not lead a document serves its clients | Accepted | A client lands on whichever node the load balancer chose, and one node leads a given document; those are independent, so a node routinely holds clients for a document it does not lead. Redirecting them is the sticky session ADR-012 rejects, and would be stale the moment a lease lapsed. So: **every node holding a document is a replica and the leader is only the writer.** A submission arriving at a relay is published to the document's inbox; the leader orders it as it orders anything and publishes the result to the document's channel; **every node applies from that channel, including the leader that wrote it** — one code path for "an operation was committed" rather than one for local and one for remote, since two paths is where they drift apart silently. The batch names the writing client and sequence, so the node holding that client acknowledges and the rest apply: no acknowledgement has to be routed back, so none can be routed wrong. Pub/sub loses messages without saying so, so a batch that does not follow directly is **not** applied — the node catches up from the log, which is the authority while the channel is only a prompt. Rejected: direct node-to-node (needs every node individually addressable, and a second transport, auth and reconnect story); a leader-only copy (a lease lapse becomes a rehydrate for everybody). Standalone is untouched. See [63](63-COLLABORATION-RELAY.md). |
| ADR-018 | Where text shaping belongs, and where it does not | Accepted | The render backend outlines glyphs per `char`, which is wrong for Arabic, Hebrew, Hindi or Thai, and the recorded fix was "add `parley`". Checking first changed the answer: the **editor draws text with `ctx.fillText`**, so the browser already shapes what a user looks at — and `casual-calc-render` is compiled into a WebAssembly bundle that is already 12.9 MB, so adding a shaping stack there taxes every editor user to fix a defect none of them can see. The real defect is the **headless PNG backend** (thumbnails, previews, server-side rendering), where a picture of somebody's Arabic document is simply wrong. So shaping goes in behind a feature: **on for native, off for WebAssembly**, where the browser has a shaper already. The unshaped path stays as the fallback and **says** it lacks shaping rather than silently producing wrong output. Rejected: adding it unconditionally; shaping in the host and passing glyphs down, which would make the same document render differently on a server than in a tab. See [64](64-TEXT-SHAPING.md). |
| ADR-019 | The dual-host capability seam is per capability, not one trait | Accepted | Four documents state in the present tense that the engine depends on a small host-capability trait; **no such type exists**, three phases past its Phase 0 deadline. What grew instead is three separate seams, and checking first changed the answer: they are **better** apart. A clock, a cancellation source and a thread pool share only the property that the engine cannot supply them — not enough to make them one interface, and a combined trait would force the browser host to stub the third of it that has no threads. Each seam is also narrower than a trait method could be: `Instant::now` **panics** on `wasm32`, so `fn now() -> Instant` is unimplementable there, while `Cancel` being `Fn() -> bool` lets a browser close over `performance.now()` and keeps every clock type out of `casual-calc-model`. The clock is a *value* rather than a method so it cannot change mid-recalculation. There is no threading seam because nothing is parallel yet, and an interface designed against no caller on a target that cannot implement it is a guess. **Proposes:** reject the single trait; accept capability-per-seam; replace boundary invariant 7's wording with "no engine crate names a platform", which is checkable and now checked — `tools/check-host-seams.py` fails on a `cfg(target_*)` in `crates/`, passing today at zero. The one real divergence is named: `casual-calc-render` gates shaping behind a Cargo *feature* (ADR-018), which is a dependency chosen per build rather than the engine branching on where it runs. Blocks `TAURI-001`. See [78](78-HOST-CAPABILITY-SEAMS.md). |
| ADR-020 | Coordinator availability: Sentinel, and a durability floor that refuses | Accepted | Redis replication is asynchronous, so a promotion can drop an append the primary already acknowledged — contradicting ADR-014 §4's one durability promise. **Sentinel** for failover, over Cluster mode: nothing here needs sharding, the append script names two keys per document so Cluster would need hash tags and a keyspace migration to buy nothing, and Cluster does not make a failover safer — each shard is a primary with asynchronous replicas and the same loss window. **`min-replicas-to-write` is the decision, not a detail**: with it, a collapsed in-sync set makes the primary **refuse** rather than accept a write it will lose, and that refusal is a shape ADR-012 already defines, `DEP-04` already reports and clients already handle. Silent loss becomes a visible outage, which is the trade taken deliberately. The node **verifies** the setting on the coordinator at startup *and after every re-resolution*, because it is per server and the standard mistake is configuring the original primary and nothing else — which passes a startup check and fails exactly when it matters. **What the design note did not foresee**, found by building it: `SENTINEL FAILOVER` demotes the old primary *in place*. The socket stays healthy, reads keep working, and every write returns `READONLY`, which the driver classifies as not worth retrying — so a re-dial reaches nothing and the node refuses every edit for the rest of its life. Re-dialling cannot fix that; **re-resolving** can, and that is why the trigger is the error and not the socket. See [77](77-COORDINATOR-AVAILABILITY.md). |
| ADR-021 | Geometry in the display list, so one plotter serves both | Accepted | Charts were drawn by ~300 lines of `webapp/editor.js` and not at all headlessly. A charting crate **fails `RND-11`'s own gate by construction** — a third-party plotter draws a third-party picture, so "a PNG of a chart sheet matches the canvas" would require rewriting the canvas — so the plotter moves down instead, and `PaintItem` gains `Polyline`, `Polygon` and `Wedge`. **That is a different kind of variant from the leaf ones and the ADR turns on the distinction:** `DataBar` and `Image` name a thing layout already resolved and leave only device questions, adding no expressive power. A geometry variant names no domain thing at all — a `Polygon` can be a bar, a swatch, a cell background or any picture — so every future backend must own a path rasteriser, a rectangle acquires two spellings, and plot construction becomes a layout responsibility. The backend floor is stated as a requirement: stroke an open polyline, fill a polygon by non-zero winding, fill an **annular** sector, centre a text run. Angles are degrees clockwise from twelve o'clock — Excel's convention, not the raster APIs' — and a doughnut's hole is a hole in the geometry rather than a disc painted over a pie, because a headless backend knows neither the background's colour nor its opacity. Rejected: a single general `Path` variant, which covers everything and is checkable for nothing. See [80](80-CHART-DISPLAY-LIST.md). **Accepted on the evidence of being built**: `RND-11` shipped to it and closed — all seven chart kinds draw model-to-PNG, `PaintItem::Polyline`/`Polygon`/`Wedge` are in the display list and the renderer has an arm for each, and the backend floor this ADR states as a requirement is met by the one backend there is. It stayed `Proposed` through all of that, which is what `tools/check-adr-status.py` now prevents: a decision a finished row was built to is settled, whatever the register was last told. |
| ADR-022 | Detection below the format crates, dispatch above them | Accepted | [19](19-WORKSPACE-SCAFFOLD-DESIGN.md) described `casual-calc-io` as "the adapter registry… the single entry point hosts call to open/save a spreadsheet without naming a format". It was not one: it depended on `-model` and `-layout` alone, and had no identity, no detection and no dispatch — it was the delimited-text adapter plus two helpers. Dispatch had grown in `casual-calc-sdk`, which chose a format from a **filename extension** and never from the bytes. **Restating the document as whatever the code grew into was the failure mode to avoid** (`ODS-01`): the registry was a structural decision about where format knowledge lives, and quietly rewriting it would have erased that decision without anybody making it. So the design is amended in two halves rather than abandoned. **Detection moves down** into `casual-calc-io`, where it belongs precisely because it needs no format crate — a zip's first local file header names its first entry, and ODF requires `mimetype` to be first *and stored uncompressed* so a reader can identify the document without decompressing it. **Dispatch stays in the SDK**, which is the entry point hosts actually call and the only layer that already depends on every format crate. The alternative — giving `-io` dependencies on `-import`, `-export` and `-ods` so the graph matched the sentence — was rejected: it would make a consumer that wants the CSV reader carry the entire OOXML and ODS stack, and would move format knowledge *away* from the layer that exists to hold it. What this buys, beyond agreement between a document and a graph: a host with an upload and no reliable filename can open it, and a mislabelled `.xlsx` that is really an `.ods` opens correctly. The engine already refused to believe a file's claim about itself for the **pictures** inside a workbook (`foreign_format` sniffs magic numbers); it now refuses for the workbook too. Detection returns `None` rather than guessing, because "probably a CSV" applied to a binary file produces a sheet of mojibake. |
| ADR-023 | The desktop shell wires the SDK inline; there is no `casual-calc-tauri` crate | Accepted | [44](44-TAURI-DESKTOP-SHELL-DESIGN.md) draws `casual-calc-tauri` as "optional thin glue" and leaves its existence open; it blocks `TAURI-001`, because a crate is a promise to keep an interface and the cheapest moment not to make one is before anybody depends on it. **A crate earns its place by having more than one consumer.** This one would have exactly one, sitting between two things that are already interfaces — the SDK's `WorkbookSession`, public by design, and Tauri's own command macros. A wrapper around a wrapper is not a seam; it is somewhere for the two sides to drift. **The glue is already demonstrated to be thin**: `RND-10` moved the browser editor onto the engine's display list, so `editor.paintlist.js` takes a `DisplayList` and paints it and the canvas owns no drawing of its own — which is exactly the shell's job as `44` states it. That half of the desktop app is code that exists and is tested, not code a crate would abstract over. The SDK already answers what a shell asks: `layout(sheet, viewport) -> DisplayList` is the whole rendering contract. **And it is the reversible direction** — extracting a crate later from working code is mechanical, withdrawing a published one is not. `SDK-009` is the standing reminder of what a second published surface costs when added before it has to be. **Proposes:** the app is a binary depending on `casual-calc-sdk` and Tauri and nothing else of ours, in **its own Cargo workspace** the way `fuzz/` is, because Tauri's tree is large and every `--workspace` build in CI would otherwise carry it — with the `cargo check` gate `CI-014` had to add for `fuzz/` after a signature change broke it silently, present from the first day rather than after it breaks once. Leaves undecided, because each needs a running shell to measure: the Tauri IPC transport cost, the native GPU backend, and parallel-recalc partitioning. See [81](81-DESKTOP-SHELL-COMPOSITION.md). |
