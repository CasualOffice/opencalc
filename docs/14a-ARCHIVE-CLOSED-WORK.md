[14](14-EXECUTION-TRACKER.md) verbatim.

**This file is not read during normal work.** It exists so that closing a row
costs nothing and the live tracker stays the size of the work actually in front
of you — 244 closed rows were 84% of that document and 46,000 of its 55,000

next to the diff, where `git log -S` and `git blame` will find it. Newer rows are

| UX-GRID-01 | Typing a reference into a formula tears the grid | Done | P1 | **Reported by the user:** typing `=2*A2` sent the canvas "to a weird place". It was worse — the column headers left the screen, one band of rows drew, and the in-cell editor detached and floated near the bottom of the window. **Root cause, found by measuring rather than reading.** The grid scrolls *virtually*: the canvas is one screen tall and draws whatever `state.scrollY` says, which is AGENTS.md's no-DOM-as-source-of-truth rule applied to scrolling. `.grid-wrap` had acquired a native `scrollTop` of 282, so the canvas kept drawing from the engine while the element it lives in had moved underneath it. Instrumenting each keystroke showed `scrollHeight` jumping 531 → 815 on the exact character that completes `A2`, and hiding children one at a time named the in-cell `<textarea>`. The cause was one CSS rule: `.formula-bar input#formula-input.tinted, textarea.inline-edit.tinted { position: relative }`, where `.tinted` is added the moment a reference is recognised. `relative` leaves an element **in flow**, so the textarea went back to being laid out after the full-height canvas — `offsetTop` 795 — with its `top` only shifting it visually; the wrapper's scroll box grew by the offset and the browser scrolled that hidden-overflow container to reveal the focused editor. Nothing about the symptom pointed at CSS. **Fixed at the cause:** the rule wanted `z-index: 1` to sit above the reference mirror, and only the formula bar's input needed `position` to accept one — the in-cell editor is *already* `absolute`. The declaration is split, and the in-cell editor keeps `absolute`. **Gated by** a browser test asserting the invariant — the wrapper never scrolls and its scroll box never exceeds its client box, checked after every keystroke — plus that the header band is still drawn, so any future element escaping containment fails it too. Mutation-verified live: reintroducing `position: relative` gives 815 against a 531 client box and `offsetTop` 795; removing it restores 531/531 and 264. **Two wrong turns, recorded because they cost time:** `focus({ preventScroll: true })` was applied first and did not fix it (kept, since it is correct on its own terms); and a `scroll` listener that reset `scrollTop` **froze the renderer** — assigning scroll position inside a scroll handler loops — and was withdrawn. Both were patches over a cause that had not yet been found. |
| UX-SCROLL-01 | Scrolling leaves a partial column (and row) against the leading edge | Done | P1 | **Reported by the user** from real use on a table: *"as scroll right, rows width shrink; on moving left it expand again; based a column; these behaviour is not constant."* **Reproduced in Chrome** against a 60-column table before anything was changed, and the reproduction is what identified it: arrowing to `AE` left a sliver of column J — the tail of one glyph — jammed between the row header and column K, with K's header label sitting over a column whose left edge was cut off. `ensureVisible` scrolled by the **bare minimum**: `state.scrollX = cL + cW - viewW` puts the target's right edge exactly on the viewport's right edge, which leaves the *leading* edge wherever it happens to fall inside another column. The leftover is a different size for every target, so the first visible column appears to change width as the selection moves — and scrolling back makes it whole again. That is precisely "not constant": there is no single wrong width to notice, only a width that never settles. Excel never shows a partial leading column. **Both axes, because it is one defect.** The row branch is the same arithmetic and leaves a partial row against the top; fixing only the axis that was reported would leave the identical bug behind the identical mechanism. **Snapping *up* to the next boundary**, never down: it only ever scrolls further in the direction already being travelled, so the cell that prompted the scroll stays on screen. The cell's own leading edge is the limit and the answer when it is wider or taller than the viewport — there no aligned offset can show it, and showing it wins over aligning. Rows go through `rowAtPx`/`rowOffsetPx` rather than the engine directly, since a row grown by wrapped or rotated text is taller than the engine believes and those two are the pair that knows it. Body-space against absolute-sheet-pixel coordinates is converted explicitly, because getting it wrong would misalign **only** on a sheet with a frozen pane — the kind of thing that survives a demo. Wheel and drag scrolling are untouched and stay smooth, which is what Excel and Sheets both do; snapping belongs to navigation. **Gated by** a browser test that drives the editor's own `select` and asserts `scrollX`/`scrollY` are members of the engine's actual boundary lists, over six targets forward and back — one jump could land on a boundary by luck. Column widths and row heights are deliberately **uneven** (`40 + (c*17)%60`), so an implementation that snapped to `round(px/width)*width` fails; and each target is also asserted still visible, since an "aligned" offset that hid the cell would satisfy alignment and defeat the point. Two new test-only exports (`scrollStateForTest`, `selectForTest`) because the grid is a canvas: a pixel test would be a test of what a column boundary is guessed to look like, and `selectForTest` routes through the real `select` rather than reimplementing it. **Mutation-verified:** restoring `scrollX = cL + cW - viewW` fails with `scrollX 951 after going to r80c30 is not a column edge` against edges `[0, 40, 97, 171, 262, 310, 375, 457, 556, 612, …]`; and the same revert reproduces the sliver in Chrome by eye. |
