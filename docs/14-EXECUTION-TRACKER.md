# 14 — Execution Tracker

**The single source of truth for the live state of all OpenCalc work.** Nothing
is worked on without a row here; nothing merges without its row updated. This is
the discipline: *track everything, update as it moves.*

## How to use this tracker

- **Every unit of work gets a row** with a **stable ID** the moment it starts
  (design, code, docs, fixtures, CI — all of it).
- The ID is the **cross-reference key** used everywhere else: PR titles,
  changelog entries, design-note "Tracker IDs" sections, and ADRs all cite it.
- **Update the status as it moves** — never let a row go stale. If a row is
  wrong, fix it in the same PR that made it wrong.
- IDs are **never reused.** A dropped item is marked `Dropped`, not deleted.

## ID scheme

`<PHASE>-<NNN>`, zero-padded, assigned in creation order within a phase:

| Prefix | Phase |
| --- | --- |
| `DOC-###` | Documentation-phase work (this repo's current state) |
| `F-###` | Phase 0 — Foundation |
| `P1A-###` | Phase 1A — Import & model |
| `P1B-###` | Phase 1B — Semantic writer |
| `P1C-###` | Phase 1C — Grid layout |
| `P1D-###` | Phase 1D — Grid render & virtualization |
| `P1E-###` | Phase 1E — Browser grid editor |
| `P2-###` | Phase 2 — Formula & calc engine |
| `P3-###` | Phase 3 — Spreadsheet features |
| `MNT-###` | Cross-cutting maintenance |

## Controlled status vocabulary

Use exactly these values — no ad-hoc statuses:

`Not started` · `Researching` · `Designing` · `Finalizing` · `Ready` ·
`In progress` · `Blocked` · `In review` · `Done` · `Dropped`

- **Ready** means: design finalized, ADRs accepted, acceptance gates defined —
  cleared to implement.
- **Blocked** must name the blocker (another ID, a decision, an upstream dep).

Every other menu in the application is a labelled list, and a collapsed group *is* a menu. Now laid out as one: full-width rows, icons at a fixed offset so the labels align and the list scans. The label is drawn from the button's own tooltip via `content: attr(data-tip)`, so there is no second copy of the string to translate and none to fall out of step — the i18n pass rewrites `data-tip` and the label follows, which is only true because [UX-B05](#) made those translatable in the first place. Controls that are not icon buttons — the font box, the size field, a colour swatch — keep their own shape and take a row each. Verified on Tools (three buttons) and Font (two selects plus two buttons). |

| COL-07 | The snapshot store: cadence, retention, and verification | Done | ADR-011's snapshot model, and nearly free to build because ADR-010 already gives a deterministic byte-stable serialization — a `Snapshot` is those bytes plus a revision number, not a format anyone had to design. Four things fall out of it. **The log stops growing**, compacted behind each snapshot. **A late joiner costs the same as a fresh one**, getting a snapshot and a tail rather than a year of history. **Cold start is a read, not a replay**, which is what makes serverless compute viable at all: a Durable Object hibernates after ten seconds and discards its memory, so for an intermittently-edited document a cold start is not a rare event to amortise but the normal case. **And bounded offline gets a defined edge** — compaction deliberately keeps a margin of `every × retain_intervals` operations behind the snapshot, so a client away across a single boundary is still rebasable rather than reloaded, and one past it is refused *with the range it needed*. The cadence defaults to 200 revisions, an order of magnitude under ShareDB's thousand, because our operations are coarse (a `Batch` paste is one operation carrying a hundred thousand cells) and our snapshots are cheap; both numbers are starting points to benchmark against time-to-first-paint, and are documented as such rather than presented as derived. The property worth having on purpose: a stored snapshot can be **verified rather than trusted** — replaying the log from an earlier one must reproduce it byte for byte, and a mismatch means the document and its history have diverged, which is corruption however it arose and is surfaced rather than repaired. Seven tests including a simulated hibernate-and-wake. Mutation-tested before being believed: verification always succeeding, the cadence off by one, compaction dropping its margin, and the retained-window bound ignored are all caught. |

| COL-08 | Collaboration server boundary | Proposed | [ADR-012](08-ADR-REGISTER.md) / [docs/57](57-COLLABORATION-SERVER-BOUNDARY.md). A server that is **an editing session, not a filing system**: it coordinates co-editing and carries auth, admin, telemetry and configuration — the concerns that only exist once a deployment does, which is why they live here and not in the SDK — while the integrator keeps the document of record and receives finished bytes through a webhook callback. **The two prior arts named are not interchangeable, and only one fits.** Excalidraw's server relays *encrypted* messages and does no centralized coordination; a relay that sees ciphertext cannot transform anything, which is exactly why Excalidraw reconciles on the client. Taking that path would reopen ADR-011 rather than deploy it. OnlyOffice's shape is what already exists here: `ServerSession` + `Snapshot` *is* a document server, and its storage model — the host downloads the finished file through a callback — is the part the request was actually about. **The finding worth having is a fidelity trap only this path could walk into**: ADR-007 makes retained bytes authoritative for everything the model does not represent, and that table is built by importing the *file*. A session started from a model-only snapshot would converge perfectly and write back a document with every unrecognised chart, VBA part and `customXml` silently removed — the exact failure the whole fidelity effort exists to prevent, reachable only through collaboration because it is the only path that reconstructs a document from something other than the bytes it arrived as. So the session's durable state is original bytes + snapshot + log, and a session that cannot obtain the original bytes refuses to start. Webhooks now, WOPI kept unforeclosed behind an interface — it is roughly ten times the work for a payoff that is admission to the SharePoint ecosystem, which is a customer-driven reason and not an architectural one. The server is a **host, not a layer** (AGENTS.md: the engine computes, the host decides I/O): it lives under `server/`, nothing in `crates/` may depend on it, and it releases on its own `server-v*` tag. **Then the hard requirement arrived — horizontal scale, no sticky sessions — which looks like it contradicts ADR-011** and is the most useful thing in this row. OT needs one serialization point per document; the naive way to get it is an owner node, which is exactly the stickiness being rejected. The resolution is to notice that the point must be *one*, not one **node**: make it the **datastore**. Every node runs the same `commit`, and the append is *conditional* on the document still being at the revision the node read — the database decides the order, so any node may accept any connection for any document. A failed compare-and-swap is not a special case, it is `transform` against the handful of operations that won, which is what this layer does anyway, and it doubles as a cache-invalidation signal naming how far behind the node is. Nodes hold only caches — workbook, revision and the original bytes the retention path needs — rehydrated from snapshot-plus-tail, which is what COL-07 exists to make cheap. **The genuine price is fan-out**: without affinity a document's participants are spread across nodes, so a committing node must reach nodes it does not know about, which needs per-document pub/sub. Worth paying — fan-out is a well-understood horizontally scalable problem, whereas affinity is an operational tax on every deploy, restart and rebalance forever. Rejected alternatives: a **per-document lease** is affinity wearing a different hat, buying lease-expiry tuning and split-brain to avoid a conditional write; a **single-writer actor** (Durable Objects) is a good fit and the platform supplies the affinity rather than the operator, but binds to one vendor — and the compare-and-swap design does not foreclose it, since the object simply becomes a very effective cache in front of the same conditional append; a **partitioned log** is correct and is a broker to operate for one conditional write per commit. To be measured before it is believed: commit latency under contention and the retry rate as concurrent editors on one document rise. Five open questions; not Accepted, no code. **Refined to a cluster with a leader per document.** A client connects to any node — that is the requirement, met at the load balancer, which stays dumb — while inside the cluster one node **leads a given document** and the rest relay to it, so a commit is the in-process `ServerSession::commit` that already exists rather than a storage round trip per operation. That matters because operations are small and frequent: paying a database write on each one puts the datastore on the typing path. This is not sticky sessions reintroduced: stickiness is affinity a *client* is subject to, and leadership is internal, cluster-assigned, and moves on its own. **The synthesis worth keeping is that leadership is an optimisation for latency while the conditional append is what makes divergence impossible** — the leader is not trusted to be unique, so it still appends conditionally on the revision and a stale leader is told *no* by the store and steps down. Neither half suffices alone: election without the guard is correct only while the election is, and the guard without a leader puts a round trip on every keystroke. It also means election can be a cheap TTL lease rather than a consensus protocol, because getting it briefly wrong costs a rejected append, not a corrupted document. Failover needs nothing from the client — `ClientSession` already holds its chunk until acknowledged, which falls out of the one-chunk-in-flight rule rather than being designed for this. |
| COL-09 | Submissions need an idempotency key | Ready | Exposed by COL-08's failover analysis, and required before the server runs rather than optional hardening. A leader can commit a chunk and die **before acknowledging it**; the client, having had no acknowledgement, resends, and the new leader cannot tell a lost chunk from a duplicate — so it applies it twice. Typing a value twice is invisible; inserting a row twice is not. `Submission` needs a client id and a per-client sequence number, with the server recording the last sequence accepted from each client and treating anything at or below it as already committed. Small, on a type that is already written. |
